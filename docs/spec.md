# Spec: PUBLISH_MODE as an interactive install-time prompt

## Summary
Surface the existing `PUBLISH_MODE` (`tailscale` vs `none`) and `BASE_URL` runtime config values as interactive prompts in `install.sh` and `ct/create.sh`, the same way those scripts already prompt for `AUTH_MODE` and other setup decisions, so choosing tailscale publishing no longer requires a manual `switchboard.env` edit + `systemctl restart ai-dev-switchboard` after the fact.

## Goals
- `install.sh` prompts for `PUBLISH_MODE` (default `none`) interactively, following the exact pattern already used for `AUTH_MODE` (the `prompt()`/`interactive()` helpers at install.sh:72-82, `get_env`/`set_env` for idempotent re-runs).
- When `tailscale` is chosen, `install.sh` also prompts for `BASE_URL` (the tailnet hostname), matching how the `AUTH_MODE=pve` branch conditionally prompts for `PVE_HOST` today (install.sh:161-164).
- `ct/create.sh` (the Proxmox-host wrapper) gets its own equivalent prompt using its existing `menu()`/`ask()` whiptail helpers (already used for `AUTH_MODE` at ct/create.sh:45-47 and the `WITH_GIT_HOSTING`/`WITH_CODE_SERVER` `yesno()` prompts), and writes the answer directly into the `TMP_ENV` heredoc it already pushes into the container (ct/create.sh:96-108) — replacing today's hardcoded `PUBLISH_MODE=none` line. `ct/create.sh` does **not** rely on `install.sh`'s own prompt for this, because it always invokes `install.sh --yes` (ct/create.sh:113-118), which never runs interactive prompts (see `interactive()`'s `[ "$YES" -eq 0 ]` check) — same reason `AUTH_MODE` is already asked independently in both scripts today.
- Both scripts' non-interactive paths (`--yes`, or `ct/create.sh`'s whiptail flow specifically) are unaffected in shape — they still end up with a real `PUBLISH_MODE=`/`BASE_URL=` line in `switchboard.env`, just sourced from a prompt instead of hand-editing after install.
- Update `README.md`'s "Reaching the UI" section and `config/switchboard.env.example`'s `PUBLISH_MODE`/`BASE_URL` comments to reflect that these are now asked at install time, with manual editing + restart remaining available as the way to *change* the choice later (not the only way to *set* it).
- `install.sh`'s final "Done" summary block gets one new conditional line when `PUBLISH_MODE=tailscale` is chosen, reminding the operator of the one manual step this spec deliberately does not automate (see "Proposed approach" below): running `tailscale serve` for the main UI itself. `ct/create.sh`'s final `SUMMARY` message gets the equivalent addition.

## Non-goals
- Not installing or authenticating `tailscale` itself (`apt-get install tailscale`, `tailscale login`) — neither script does this today for any purpose, and it's out of scope here.
- Not automating the main switchboard UI's own `tailscale serve --bg https+insecure://127.0.0.1:$LISTEN_PORT` invocation (README.md:120-121) — see "Proposed approach" for why, and the flagged item under "Open questions".
- Not changing anything about how `PUBLISH_MODE`/`BASE_URL` are *read* at runtime (`app/app.py`'s `_publish()`/`_unpublish()`, app.py:399-415) — that logic is correct today and untouched by this item.
- Not adding input validation/re-prompt-on-bad-value beyond what `AUTH_MODE`'s prompt already does (i.e. none) — see "Edge cases".
- Not touching `docs/ARCHITECTURE.md`'s privilege-boundary text — it documents runtime behavior (which is unchanged), not the install flow, and re-reading it confirms no line there is install-flow-specific enough to need an edit for this item. Flagged here explicitly since the task description asked to check.

## Background / current state
- `PUBLISH_MODE` (`tailscale` | `none`) and `BASE_URL` are read once at process start in `app/app.py` (app.py:101-102) and used by `_publish()`/`_unpublish()` (app.py:398-415) to decide whether a per-project ttyd/code-server terminal gets published via `tailscale serve --set-path` or stays loopback-only. This part already works and is documented in `docs/ARCHITECTURE.md`'s "Processes and privilege boundaries" section (lines 31-37).
- `config/switchboard.env.example` (lines 57-75) documents both variables with a real default (`PUBLISH_MODE=none`, uncommented) and a commented-out `#BASE_URL=` placeholder. Today, setting `PUBLISH_MODE=tailscale` requires manually uncommenting/editing this file post-install and running `systemctl restart ai-dev-switchboard` — there is no prompt for it anywhere in `install.sh` or `ct/create.sh`.
- `install.sh` already has the exact prompting machinery this item needs: `interactive()`/`prompt()`/`prompt_secret()` (install.sh:72-82), `set_env`/`get_env` for idempotent upsert (install.sh:83-93), and a working precedent in the `AUTH_MODE` block (install.sh:158-177) — including the conditional-follow-up-prompt pattern (`PVE_HOST` only asked when `AUTH_MODE=pve`) that `BASE_URL` should reuse.
- `ct/create.sh` already prompts interactively for `AUTH_MODE` via its own `menu()` whiptail helper (ct/create.sh:45-47) and for `WITH_GIT_HOSTING`/`WITH_CODE_SERVER` via `yesno()` (ct/create.sh:56-64), then bakes every answer straight into the `TMP_ENV` heredoc (ct/create.sh:96-108) it pushes into the freshly-created container before running `install.sh --yes` inside it. It currently hardcodes `PUBLISH_MODE=none` in that heredoc (ct/create.sh:104) with no prompt at all.
- `README.md`'s "Reaching the UI" section (lines 114-129) already documents the tailscale/SSH-tunnel/reverse-proxy choice manually, including the exact `tailscale serve` command for the main UI and the instruction to "Also set `PUBLISH_MODE=tailscale` and `BASE_URL` in `switchboard.env`" (line 122) — that phrasing is what needs updating once setting them no longer requires a manual file edit.

## Proposed approach
1. **`install.sh`**: insert a new `-- Publishing --` prompt block after the existing `AUTH_MODE`/auth block and before the `WITH_HOST_CONTROL` check (i.e. around today's install.sh:177-179), following the `AUTH_MODE` block's exact shape:
   - `PUBLISH_MODE=$(prompt "Publish per-project terminals via tailscale serve, or keep them loopback-only?" "$(get_env "$ENV_FILE" PUBLISH_MODE)")`, defaulting to whatever's already in `$ENV_FILE` — which is `none` on a first install (freshly copied from `config/switchboard.env.example`, whose `PUBLISH_MODE=none` line is not commented out) and whatever was previously chosen on a re-run, matching the idempotent-re-run guarantee `install.sh`'s own header comment already promises ("never clobbers switchboard.env values that are already set").
   - `set_env "$ENV_FILE" PUBLISH_MODE "$PUBLISH_MODE"`.
   - If `[ "$PUBLISH_MODE" = "tailscale" ]`, prompt for `BASE_URL` the same way `PVE_HOST` is conditionally prompted for today (install.sh:162-163), defaulting to any existing value, with prompt text pointing at `tailscale status` as the way to find the real hostname and explicitly allowing it to be left blank (mirrors `BASE_URL`'s existing "Required when PUBLISH_MODE=tailscale" doc comment — leaving it blank here is a valid choice, just an incomplete one until filled in, same as leaving `PVE_HOST` blank today produces an incomplete-but-not-crashing config).
2. **`ct/create.sh`**: insert an equivalent block after the existing `WITH_CODE_SERVER` `yesno()` prompt (today's ct/create.sh:61-64) and before `TOTP_SECRET` generation:
   - `PUBLISH_MODE=$(menu "How should per-project ttyd/VS Code terminals be published beyond this container?" "none" "..." "tailscale" "...")`, default cursor on `none` (first menu item).
   - If `tailscale` was chosen, `BASE_URL=$(ask "..." "")`; otherwise `BASE_URL=""`.
   - Replace the hardcoded `PUBLISH_MODE=none` line in the `TMP_ENV` heredoc (ct/create.sh:104) with `PUBLISH_MODE=${PUBLISH_MODE}`, and add a `BASE_URL=${BASE_URL}` line right after it (there is currently no `BASE_URL=` line in that heredoc at all).
3. **Sub-question the backlog flagged but didn't resolve** — whether choosing `tailscale` should also run `tailscale serve` there and then, or just set config and leave the actual command as a documented manual step: **this spec's call is to keep it manual, config-only.** Both scripts only *set the values*; they print a reminder of the exact follow-up command in their final summary output (see Goals). Rationale is under "Open questions" below since the backlog explicitly asked for this to be called out rather than silently decided.
4. **Docs**: update `README.md`'s "Reaching the UI" tailscale bullet (line 122) to say `install.sh`/`ct/create.sh` now prompt for `PUBLISH_MODE`/`BASE_URL` directly at setup time (still describing the separate, still-manual `tailscale serve` step for the main UI itself, which this item does not change). Add one short sentence to `config/switchboard.env.example`'s `PUBLISH_MODE`/`BASE_URL` comment block (around lines 57-75) noting both are asked interactively during install/`ct/create.sh`, and this file only needs hand-editing (+ `systemctl restart ai-dev-switchboard`) to *change* the choice afterward.

## Affected areas
- `install.sh` — new prompt block (~10 lines) plus one new conditional line in the final "Done" summary. Single file, single layer (install-time shell scripting).
- `ct/create.sh` — new `menu()`/`ask()` prompt block (~10 lines), one changed + one added line in the `TMP_ENV` heredoc, one new conditional line in the final `SUMMARY` string.
- `config/switchboard.env.example` — comment-only edit, no functional/schema change (the `PUBLISH_MODE=none` default line and `#BASE_URL=` placeholder stay as-is).
- `README.md` — wording update to the "Reaching the UI" section's tailscale bullet only.
- No changes to `app/app.py`, `docs/ARCHITECTURE.md`, or any data model/API/schema — this is purely an install-time UX change surfacing an already-correct runtime config path.

This is a single, small, single-layer (install scripting + docs) change — no load-balanced-decomposition split needed.

## Edge cases
- **Non-interactive installs (`install.sh --yes`, or `ct/create.sh`'s own non-interactive `CT_*`/`SWB_*` env-var path mentioned in its header comment)**: prompts must not block. `install.sh`'s `prompt()` already handles this via `interactive()`'s `[ "$YES" -eq 0 ] && [ -t 0 ]` check — under `--yes` it silently falls through to whatever default (existing `get_env` value, i.e. `none` on first install) with zero behavior change from today. `ct/create.sh`'s whiptail `menu()` always runs (it has no `--yes`-style bypass for its own prompts today, same as its existing `AUTH_MODE`/`yesno()` prompts) — consistent with how it already behaves for every other setting.
- **Re-running `install.sh` on an existing install**: per its own header comment ("never clobbers switchboard.env values that are already set" — though in practice `set_env` always upserts to whatever's just been prompted), the prompt defaults to the currently-configured value (via `get_env`) so hitting Enter is a no-op re-affirmation, not an accidental reset to `none`.
- **`tailscale` chosen but `BASE_URL` left blank**: allowed, matches today's already-tolerant handling of an unset `BASE_URL` (per-project publish URLs would just render as `<path>` with an empty prefix) — not a new failure mode introduced by this change, just reachable slightly earlier (at prompt time instead of only after a manual edit).
- **Typo'd or unrecognized `PUBLISH_MODE` value** (e.g. "Tailscale" capitalized, or a stray typo): no new validation is added, matching `AUTH_MODE`'s existing precedent of accepting free text with no re-prompt loop. `app.py`'s existing `if PUBLISH_MODE == "tailscale":` check (app.py:400) already treats anything else as `none`-equivalent behavior regardless of the literal stored string, so this is a pre-existing tolerance, not a new risk surfaced by adding the prompt.
- **`ct/create.sh` container path**: the per-project terminal publish behavior itself only takes effect once `install.sh --yes` runs inside the container with `PUBLISH_MODE`/`BASE_URL` already present in the pushed `switchboard.env` — no ordering issue, since `install.sh` never overwrites an already-existing `$ENV_FILE` (install.sh:145) it only upserts individual keys into it.
- **Platform differences**: none — both scripts are Debian/Ubuntu-only already; no new platform surface introduced.

## Acceptance criteria
- [ ] Given a fresh `sudo ./install.sh` run with a TTY attached and no `--yes`, when the installer reaches the new publishing prompt, then it asks for `PUBLISH_MODE` with default `none`, and typing `tailscale` triggers a follow-up prompt for `BASE_URL`.
- [ ] Given `PUBLISH_MODE=tailscale` and a `BASE_URL` value entered, when the install finishes, then `/etc/ai-dev-switchboard/switchboard.env` contains real `PUBLISH_MODE=tailscale` and `BASE_URL=<value>` lines (via `set_env`'s upsert), with no manual file edit required.
- [ ] Given `sudo ./install.sh --yes` (non-interactive), when the installer runs, then it does not block waiting for publishing input and `PUBLISH_MODE` ends up whatever was already in `switchboard.env` (or `none` on a first install) — identical behavior to today.
- [ ] Given a re-run of `install.sh` on a box that already has `PUBLISH_MODE=tailscale`/`BASE_URL=foo.ts.net` set, when the publishing prompt is shown, then the presented default is `tailscale`/`foo.ts.net` (not `none`/blank), and pressing Enter on both preserves the existing values.
- [ ] Given `ct/create.sh` run interactively on a Proxmox host, when it reaches the new publishing menu, then choosing `tailscale` prompts for a tailnet hostname (blank allowed), and the container's pushed `switchboard.env` contains the chosen `PUBLISH_MODE` and `BASE_URL` values instead of the previously-hardcoded `PUBLISH_MODE=none`.
- [ ] Given `PUBLISH_MODE=tailscale` was chosen in either script, when the install/creation finishes, then the final printed summary includes a reminder of the still-manual `tailscale serve` command needed for the main UI itself (this item does not run it automatically).
- [ ] Given `PUBLISH_MODE=none` (the default) is chosen, when the install/creation finishes, then the final printed summary is unchanged from today's — no new tailscale-specific text shown.
- [ ] `README.md`'s "Reaching the UI" tailscale bullet and `config/switchboard.env.example`'s `PUBLISH_MODE`/`BASE_URL` comments reflect that these are now install-time prompts, not editing-`switchboard.env`-required.

## Open questions
- **Flagged per the backlog's explicit request for a reasoned call, not a silent decision**: should choosing `PUBLISH_MODE=tailscale` at install time also run `tailscale serve` there and then (for the main UI, and/or verify `tailscale`/`tailscale login` are already done), rather than just setting the config values and printing a reminder?
  **Decision made in this spec: no — config-only, with a printed reminder of the exact manual command.** Reasoning: (1) actually running `tailscale serve` for the main UI requires `tailscale` to already be installed *and* authenticated (`tailscale login`) on the box, and neither script manages that anywhere today — adding it would be a materially bigger feature (installing + auth-flow for a third-party CLI) than "surface an existing config choice as a prompt," which is what this backlog item asked for; (2) the tailnet hostname needed for `BASE_URL` isn't knowable until *after* that login step completes, so a fully-automated flow would need to interleave "install tailscale → log in interactively (device-auth-style, can't be scripted blindly) → read back the assigned hostname → then prompt for `BASE_URL`" — a much larger, riskier change; (3) it keeps the two scripts' story consistent with what's already documented: the main UI's own `tailscale serve` command in README.md's "Reaching the UI" section is already presented as a manual one-off, and per-project terminal publishing (the part `PUBLISH_MODE` actually gates) already happens automatically and *unattended* inside `app.py`'s `_publish()` at session-start time with no install-time action needed for that part at all. If this decision should instead be "yes, automate it," that's a materially larger follow-up item, not a tweak to this spec.
- No other open questions — this item was flagged in the backlog as low-ambiguity, and the archaeology above confirmed the existing prompt patterns are directly reusable without further design decisions.

## Risk / rollback notes
- Very low risk: additive prompts in two already-idempotent, already-safe-to-re-run scripts, plus comment-only doc edits. No runtime code path (`app/app.py`) changes at all.
- Rollback is trivial: revert the two script diffs and the doc wording; `switchboard.env` itself is untouched by a rollback (existing `PUBLISH_MODE`/`BASE_URL` values, however they got set, keep working exactly as they do today since `app.py`'s reading of them is unchanged).
- Nothing here touches the sudoers/privilege-boundary surface (`docs/ARCHITECTURE.md`'s "Processes and privilege boundaries") — no new privileged operation is introduced, this only changes when an existing, already-unprivileged config value gets its value chosen.
